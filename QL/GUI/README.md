# Tangles: SSB / TurboPTR GUI proof

A small native SMSQ/E experiment: sixteen labelled RGB colours (A-P), an 8x8
paint grid, left-button dragging with interpolation, palette selection, clear,
redraw, window movement and clean exit. Board contents live in an array so they
can be redrawn after a move. This is the GUI foundation, not a puzzle player;
painting can overwrite existing cells and does not enforce Tangles rules.

## Runtime

Use an expanded SMSQ/E machine/emulator with an **800x600 or larger GD2 display**.
The integration check uses SMSQmulator's 16-bit mode 32 and 8 MiB RAM. Set the
desktop resolution/colour mode in the emulator before launching. The program
checks the available size; it does not change the user's desktop mode.

Load the SMSQ/E Turbo Toolkit and TurboPTR `TPTR_EXT` once, then execute the
compiled program. For example, after copying the files to `win1_tangles_`:

```basic
LRESPR "win1_tangles_ttk"
LRESPR "win1_tangles_tptr_ext"
EXEC_W "win1_tangles_tangles_exe"
```

Do not reload extensions already loaded in that SMSQ/E session. SMSQ/E supplies
the Pointer Environment/Window Manager. SSB and the Turbo compiler are build-time
tools. `TPTR_BAS`, SETW, QMenu and EasyPTR are not used by this proof.

- Click a colour swatch, then hold the left mouse button and drag on the grid.
- Fast movement visits intermediate cells horizontally, then vertically.
- Releasing the button stops painting. Leaving the grid breaks interpolation.
- **C** / Clear clears the grid; **R** repaints it from stored state.
- **M** / the title strip moves the window using TurboPTR's native move routine.
- **Esc** / Quit exits and releases window/heap allocations.

## Build from Windows with the existing local toolchain

Requires Python 3, a JDK (Java and javac), and the existing external
`C:\Source\Structured Super Basic` emulator/toolchain setup. It must contain
`build/compiled-app/{ssb280_exe,parser_task,codegen_task,ttk,env_bin}`,
`build/newclasses`, `build/emulator-lib` and its SMSQ/E ROM at `build/SMSQE`.
The emulator runs without opening a desktop window, but needs a graphical Java
environment because SMSQmulator creates an AWT cursor internally.

```powershell
cd C:\Source\Tangles\QL\gui
python build.py --check
```

The script downloads the reviewed TurboPTR archive from its official distributor
and verifies its SHA-256. To use an existing copy instead:

```powershell
python build.py --turboptr C:\QL\TurboPTR\tptr.ext --check
```

Use `--ssb-root` for another location of the prepared SSB toolchain.
No ROM, emulator, SSB, Turbo or TurboPTR distribution is checked into this folder.
External dependencies and generated files are confined to ignored `build/`.

The build invokes the **real QL SSB 2.8.0 translator and Turbo compiler** inside
SMSQ/E. No host-language replacement compiler is used. Outputs are in
`build/latest/`:

- `tangles_exe`: compiled 68000 executable with SFA/QemuLator metadata.
- `output_bas`: the numbered BASIC generated by SSB.
- `report`, `build.log`, `build.json`: diagnostics and source/executable hashes.
- `tptr_ext`, `ttk`: local copies of runtime dependencies.
- With `--check`: screenshots and `smoke.json` from the compiled integration run.

Transfer the executable with a QDOS-aware method that preserves its executable
header and 256 KiB dataspace. An ordinary byte copy onto a QL filesystem may
require restoring file type/dataspace metadata. Do not prepend a second header.

## Native QL build

Copy `tangles.ssb` and `build.ssb` as `tangles_ssb` and `build_ssb`, preserving
ASCII bytes and LF line endings. With the build tools/extensions loaded, adjust
the device prefixes to your own setup:

```basic
SETENV "SSBWORK=win1_tangles_"
SETENV "SSBWORK2=ram1_"
SETENV "SSBOVER=Y"
EXEC_W "win1_ssb280_exe";"build"
LOAD "ram1_build_bas"
CHARGE
```

The wrapper chooses the tested wide-code model, Brief optimisation and a 64 KiB
compiler buffer, writing `ram1_tangles_exe` and `ram1_tangles_err`. Ensure the
Turbo compiler can find `parser_task` and `codegen_task` through its device setup.

## Design and checks

`tangles.ssb` constructs a minimal new-style WMAN definition with one information
window, then uses TurboPTR's `M_SETUP`, `M_PRPOS`, `SWIN`, `BRPTR` and `BCHWIN`.
The definition follows TurboPTR's documented layout; every allocated byte is
initialised. Grid and palette drawing use SMSQ/E `COLOUR_24` RGB requests and
pixel-based `BLOCK`/`CURSOR`, independent of the graphics coordinate scale.

`GuiCheck.java` boots the real SMSQ/E ROM and runs the **compiled** executable.
It supplies mouse movement/buttons through SMSQmulator's emulated input linkage
and checks rendered pixels. It does not call the paint routines directly.
The smoke test covers all sixteen colours, dragging, skipped-cell interpolation,
release, palette selection, redraw, native window movement with state preserved,
clearing and clean exit. Covering/uncovering with another application and
additional display backends require their own checks; a recorded smoke pass
only establishes the cases listed in that run's evidence.
`validation.json` records the successful build and 32 runtime assertions, with
hashes identifying the checked source, harness, executable and dependencies.
